The thesis

VELO is not a demo that renders a verdict. It is a system with provable properties — determinism, tamper evidence, and a legal admissibility rule enforced as a cryptographic constraint rather than a promise — with a contract deployed to Midnight's live preview network. The properties are the product. The UI is how you look at them.

Track A · Platform depth

What the circuit actually binds

The most common way a ZK attestation system is hollow is that the commitment covers the surroundings of the claim but not the claim itself.

// contracts/velo.compact — the shipped circuit
commitment = persistentHash<Vector<6, Bytes<32>>>([
  pad(32, "velo:attestation:v1"),  // domain
  bundle_fingerprint,             // the analysis
  custody_tip,                    // chain of custody
  verdict            as Field as Bytes<32>,
  corroborationCount as Field as Bytes<32>,
  salt                            // 32 CSPRNG bytes
]);

// the admissibility rule, as a circuit constraint
assert(verdict != MALICE || corroborationCount >= 2);

// replay guard — round 2, finding G2
assert(!caseVerdicts.member(disclose(commitment)),
       "this attestation already exists");

The commitment shape and the replay guard are quoted verbatim from the F3 addendum and round 2. The Daubert gate line is written in the form it takes, not as a literal paste.

We found this ourselves

An earlier version hashed only [fingerprint, tip, salt], leaving the verdict a free public argument. It was vacuous in exactly the way that matters: an analysis sealed as NOISE could have been attested on-chain as MALICE. Finding F3, round 1. The verdict is now inside the thing it claims to prove.

A rule, not a promise

Attempting to attest MALICE from a single source does not produce a rejected transaction. It fails to produce a proof at all. There is no code path, admin override or flag that yields a valid attestation — the constraint is part of what valid proof means here.

The dual-ledger boundary is compiler-enforced

Public — on-chain, foreverPrivate — never leaves the machine
commitment, declared verdict, attestation_count, case_commitment bundle_fingerprint, custody_tip, verdict detail, corroboration_count, secret_salt

Nothing crosses that line unless the author marks it with disclose(). This is not a convention we follow — it is a compile error if we don't.

Three things we chose not to do

  • We do not compute the commitment in TypeScript. persistentHash is not SHA-256, and the domain and cast encodings are undocumented. Reimplementing from guesswork gives a number that looks right and is wrong.
  • We do not store evidence on IPFS or Arweave. Encryption today is not privacy forever, and a court can order evidence destroyed while a permanent p2p network cannot delete it.
  • We do not use biometrics. Biometrics proves a person exists. A judge asks whether that person is authorized — that is a credential check, not a face.

Track B · Engineering rigor

The properties, and how they are held

A verdict threshold compared with floating point is a verdict that can differ between machines. So there are no floats anywhere on the decision path.

// src/engine/scorer.ts — verbatim
const MALICE_THRESHOLD = new Fraction(33, 100);
const NOISE_CEILING    = new Fraction(8, 100);
const MIN_CORROBORATION_FOR_MALICE = 2;

// detector weights: 1/4, 1/4, 3/10, 1/5, 1/5  -> max 6/5
// largest single weight 3/10 < 33/100 threshold
// => MALICE structurally needs 2+ detector categories
//    AND 2+ independent sources. Not enforced by an if.

// comparison cross-multiplies, never divides:
// no rounding step exists between evidence and verdict
// src/seal/custody.ts
genesis_hash = sha256("VELO_GENESIS:" + caseId)
entry_hash   = sha256(canonicalize({
  seq, eventType, timestamp, detail, prevHash
}))

Fail-closed by default, in four independent places

  • No custody, no verdict. score() short-circuits to ABSTAIN before any detector is consulted. custodyValid is derived, never asserted by a caller.
  • Unscrutinized malice is downgraded. Threshold and corroboration met but an empty devil's-advocate field → degrades to SUSPICION.
  • Missing secrets throw. MIDNIGHT_STORAGE_PASSWORD has no default — it had one, in a public repo, until finding F17.
  • Malformed input yields a sentence, not a stack trace. The verifier never reaches valid: true by accident.

Canonicalization — the least glamorous part

If an opposing expert reimplements the verifier in Python and computes a different hash for an intact bundle, they conclude the evidence was altered. The bug is ours; the consequence is the victim's. Which is why keys sort by Unicode code point rather than UTF-16 code unit (F9), why non-finite, non-integer and past-2⁵³−1 numbers throw instead of coercing (F11), and why duplicate JSON keys are rejected outright (F10).

Two hashes, on purpose

analysisFingerprint excludes the timestamp and custody, so a replay of the same analysis reproduces it exactly. bundleHash includes both and is unique to this sealing. Collapsing them makes "prove you re-ran it and got the same answer" impossible.

Two canonicalizers, pinned to each other

The offline verifier duplicates the logic deliberately, to have zero dependencies. Duplication guarantees drift — the two had already diverged when we found it (F8). The fix was not to delete one: it was a conformance suite of 20 shared vectors, so drift fails a test instead of surfacing in court.

The model is out of the decision path

No LLM scores, classifies or decides anything. The scorer is deterministic arithmetic and the verdict is sealed before any narration happens. A system whose output is evidence cannot have a probabilistic component between the input and the verdict.

A limitation we wrote a test to prove

A hash chain with its last N entries deleted is still internally consistent — truncation cannot be caught by inspecting the chain alone. pipeline.test.ts contains a test asserting valid === true on a truncated chain, on purpose, so the gap is visible in the suite rather than implied in a doc. The real defense is that custody_tip sits inside the on-chain commitment. The tip is the anchor point; the ledger is the anchor.

The filter

The five things you cannot fake in ten hours

Demos accumulate features. Engineered systems accumulate negative results. Ours are in the repository, dated.

  1. A test written to prove a limitation exists. pipeline.test.ts asserts that custody truncation passes local verification. Nobody writes that test to look good. It exists so the gap cannot quietly close over.
  2. A mitigation that failed, documented as having failed. The first seed-redaction wrapper passed 10/10 under Node, was recorded as MITIGATED, and the seed printed in full on the first real deploy — because the deploy runs under Bun, which implements console natively and bypasses process.stdout.write. We rewrote the doc to say "failed on first real run" before we rewrote the code.
  3. A test that passed while the thing it tested was visibly broken. Under Bun, the script printed the seed three times in full and directly beneath asserted PASS — the seed never reaches the stream. It captured by replacing process.stdout.write, the exact mechanism Bun bypasses: the array stayed empty and !"".includes(seed) is true. A check that observes nothing passes everything. The script now spawns a child process and greps the bytes that actually came out — 10/10 under both Bun and Node.
  4. A falsified attack kept in the record. F15's prompt injection did not work. We wrote down that it did not work, and that this does not close the question.
  5. A corpus checked against its own engine. F5 found 8 of 13 demo cases diverging from their documented verdict — including one we downgraded from MALICE to SUSPICION because the real gate would not let it through.

Platform learnings

Three Midnight walls, documented

They are written down because "we understood the platform on the first try" is not a claim a hackathon project gets to make honestly.

L1 — NIGHT is not DUST

Insufficient Funds: could not balance dust on a funded wallet. Fees are paid in DUST, and DUST is not a faucet token: it is generated by explicitly registered NIGHT. The dependency has the function, its own comment says it is required, and deployMidnightContract never calls it. We found it by downloading the real published tarball from npm and tracing the call path.

dust: 0 → 1127246784999999999 after one registration transaction

L3 — Custom error 170 is not about your contract

The published answer for that error is a version bump. True for its author, false for us. 170 is InvalidDustSpendProof: the node rejected the fee proof, not the deploy proof. Everything already matched the compatibility matrix; the real cause was stale dust state. Nothing changed between the failed run and the successful one three minutes later.

dust sync: true → false → false → true in the failing run's final 30 s

The generalizable lesson

An error message names a symptom in the vocabulary of the layer that threw it, not the cause — and the first published explanation of an error is not necessarily the one that applies to you. When a message points somewhere and the obvious fix does not work, stop escalating the obvious fix and go read the code that produced the message.

Declared limits

What this does not establish

Stated plainly, because a forensic tool that overstates its own guarantee is the failure mode it exists to prevent.

In one sentence

VELO proves that a specific verdict was produced by a specific process, under specified constraints, and that the resulting attestation cannot be altered afterward. It does not replace forensic judgment; it makes forensic judgment auditable.

Separately from all of the above: VELO does not establish that the examiner's original analysis was performed honestly. That remains a human and judicial responsibility, exactly as with any forensic report today. VELO removes post-hoc tampering with a sealed verdict. It does not remove a corrupt examiner at the moment of analysis.

What ships next

The path, in order

1 · Close the loop already open

Exercise a real proof against the deployed contract with a live test vector, and replace attest_case's local_pending_contract with the real chain interaction. Converts "keys generated" into "proof accepted".

2 · Corpus and rule hygiene

Reconcile CASES.md with the 13 shipped fixtures, remove the pre-F5 generation, and fold ruleVersion into the commitment (G7) — far cheaper now than after attestations exist.

3 · Selective disclosure

A judge with standing requests the evidence; the examiner grants or denies explicitly; consent is recorded on-chain and the transfer stays off-chain and encrypted. Nothing is disclosed automatically. Later, K-of-N threshold sharing.

4 · Anonymous examiner credential

A Merkle membership proof inside the ZK proof. It is the same mechanism that closes G1's authorization half, G5's linkability and G8's revocation — which is why it is one structural piece and not three.

5 · Blind second opinion

A second examiner attests the same case_commitment independently; the contract records agreement or contradiction without either seeing the other's analysis.

6 · Before any real-world use

In-circuit source-root binding (G3), an independent adversarial audit — ours is rigorous and still self-audit — a production-grade engine, an independently published offline verifier, and a bit-for-bit determinism proof ahead of mainnet.

For the jury

Four questions, answered head-on

"It's ten hours old. How can it be serious?"

Age is not the measure; what is bound is the measure. The contract is deployed, the commitment covers six elements including the verdict itself, the admissibility rule is a circuit constraint, and the system has been attacked four times by its own authors with 27 findings written down and 21 fixed. Look at what we recorded as broken — that is the part that takes time and cannot be borrowed.

"What stops you from just attesting whatever you want?"

For MALICE from one source: the circuit. There is no proof to submit. For the deeper version — what stops a prover hand-supplying witness bytes — nothing yet, and we named it G1 ourselves in round 2 rather than waiting for you to.

"Why not just publish the evidence, or put it on IPFS?"

Because encryption today is not privacy forever, and because a court can order evidence destroyed while a permanent p2p network cannot delete it. The commitment travels; the evidence stays in the custody infrastructure of the institution holding it.

"What's the weakest part?"

That the circuit proves a relationship among the witness values it is handed, not that an engine ever ran on real evidence (G1) — and that source independence is declared rather than proven (G3), which survives even if G1 is solved. Both are in ARCHITECTURE.md, under "What the proof does and does not establish". We wrote that section before anyone asked.
