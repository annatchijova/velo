# Architecture Decision Records — MVP (ADR-001 … ADR-006)

The decisions behind the MVP defined in [`PRD_MVP.md`](./PRD_MVP.md). Each
record: context, decision, alternatives rejected, consequences. Written to be
read before implementing, and to be superseded explicitly — never silently.

---

## English

### ADR-001 — Vercel + Neon, no hosted proving

**Context.** The MVP needs the frontend reachable by anyone (J1), sealed cases
persisted and queryable (J2), and on-chain attestation status displayed (J4).
The attestation *write* path needs a proof server, LevelDB private state, an
encrypted key store and a Bun-only dependency stack — none of which can or
should run on shared serverless infrastructure (see ADR-003).

**Decision.** Host the Next.js frontend on **Vercel**; persist sealed cases
and the expert role registry in **Neon** (serverless Postgres) via Drizzle.
No hosted proving backend.

**Rejected.**
- *Vercel-only (no DB):* the MVP requires persisted, queryable sealed cases —
  in-memory or response-only state does not survive invocations.
- *Full-cloud backend (GCP/AWS/Azure):* the only genuine driver for owned
  infrastructure is server-side ZK proving, and that belongs on the expert's
  machine per the threat model.
- *Hosted proving backend:* puts signing keys and private state on shared
  infrastructure — contradicting the security story the product exists to
  make.

**Consequences.** Vercel's serverless filesystem and timeouts shape what can
run there (reads, sealing, verification — all pure compute); every
chain-write capability stays in local tooling. One managed Postgres to
operate; connection strings become the first real secrets this repo has.

### ADR-002 — Corpus served statically at build time

**Context.** The corpus (14 cases, 6 peritos) is read from the repo root at
request time via `resolve(process.cwd(), "..")` — a layout that does not
exist in Vercel's serverless runtime, where only traced files are present and
`process.cwd()` is not the repo.

**Decision.** Make the corpus API routes build-time static:
`export const dynamic = "force-static"` on `/api/cases` and `/api/peritos`;
`generateStaticParams` enumerating the corpus on `/api/cases/[id]`. Next.js
evaluates them during `next build`, when the repo layout exists; the JSON is
served from the CDN.

**Rejected.**
- *Runtime fs via `outputFileTracingIncludes` + `VELO_REPO_ROOT`:* works, but
  couples runtime behavior to Vercel-internal paths — fragile across platform
  changes.
- *Build-time copy of the corpus into `frontend/`:* a second copy of the same
  data is exactly the drift hazard red team F5 documented.

**Consequences.** Corpus changes require a redeploy — acceptable: the corpus
is committed data, so that was already true in practice. Local development
keeps reading the repo root directly (unchanged).

### ADR-003 — Local attestation, web reads

**Context.** Calling the contract's `attest` circuit requires witnesses, a
funded wallet and the local proof server; the client stack keeps private state
in LevelDB and keys in a local encrypted store. This cannot run in Vercel —
and per VELO's thesis it should not: keys and evidence belong on the expert's
machine.

**Decision.** Writes stay local: `deploy/attest-case.ts` (existing, proven on
`preview`) produces attestations; the CLI posts an attestation record
(`{bundleHash, txHash, commitment}`) to the web API (ADR-006). The web app
only reads: chain state via the existing `readOnChainLedger()` /
`GET /api/chain` (contract bindings are committed, so this runs on Vercel),
sealed cases via the database. This extends the read/write separation already
documented in [`CHAIN.md`](./CHAIN.md).

**Trust model for the verification panel — two classes, labelled separately
in the UI:**
- **chain-verified** — the commitment is present in the on-chain
  `caseVerdicts` map with the claimed verdict. Readable via `GET /api/chain`
  anywhere the committed bindings run, including Vercel.
- **expert-reported** — the commitment value itself, provided by the expert
  when posting the attestation record. The salt is private (per-case, in the
  expert's private state), so the commitment cannot be recomputed from the
  bundle alone; the linkage is anchored by API-key authentication plus bundle
  ownership (ADR-006), and by the chain-verified membership check.

**Rejected / deferred.** Browser-side attestation. The connector v4 API
exposes wallet-delegated proving (`getProvingProvider` +
`balanceUnsealedTransaction` + `submitTransaction`; 1AM sponsors proving and
dust), so this is a real post-MVP path — gated on serving the ZK assets and
the WASM/webpack configuration from the frontend, the known-painful part of
Midnight frontend work (`CHAIN.md`, "What is not built").

**Consequences.** The web app never touches signing keys or proof
generation; an expert without local tooling can seal and query but not
attest — stated in the UI, not hidden.

### ADR-004 — Wallet identity, public reads, no passwords

**Context.** Experts need an identity attached to persisted seals (J2).
Midnight's connector API v4 (`ConnectedAPI`) exposes addresses, balances and
configuration — but **no message-signing primitive**, so cryptographic
possession proof is not available through the official API surface.

**Decision.** Roles: anonymous (browse/demo, nothing persists), expert
(wallet connected + present in the role registry → persists and attests),
reviewer/judge (no account — public reads and the `/verify` panel).
Authentication = wallet connect; the client presents the connected wallet
address, the server issues a signed httpOnly JWT cookie (`AUTH_SECRET`). No
passwords, no email, no OAuth.

**Known limitation (accepted).** The address is UI-attested: the server
trusts what the connected client reports. This is sufficient for MVP role
gating (attaching identity to actions, not protecting secrets); it would not
be sufficient for anything financial. Possession-proof hardening is post-MVP
and would need a signing surface the official connector does not provide
today.

**Consequences.** Zero credential management for users; the role registry
(`experts` table, seeded with the synthetic peritos) is the single source of
role truth; unknown wallets can connect but cannot persist (AC-J2.6).

### ADR-005 — Monorepo deployment configuration

**Context.** npm workspaces monorepo: the frontend depends on the root `velo`
package (`file:..`, resolved to `./dist/src/*`), so the root package must be
compiled before `next build`. Vercel needs unambiguous install/build
instructions, and the nested `frontend/package-lock.json` (left in place —
repo cleanup is out of scope) could otherwise confuse lockfile resolution.

**Decision.** Vercel project: Root Directory `frontend`, framework Next.js,
Node 20+. `frontend/vercel.json` sets an explicit `installCommand` (`cd .. &&
npm ci` — always resolve from the workspace root lockfile) and `buildCommand`
(`npm run build:deploy` = root `tsc` then `next build`). `next.config.mjs`
sets `outputFileTracingRoot` to the repo root and `outputFileTracingIncludes`
for everything loaded through runtime-computed paths: `contracts/velo.compact`
(the root marker), `contracts/managed/**` (committed bindings),
`deploy/managed-shim/*.json` (contract address artifact), `cases/*.json`,
`peritos-syntetic/*.json`.

**Rejected.** Restructuring the monorepo for simpler deploys — the workspace
layout is load-bearing for local development and for the frontend's direct
imports of the engine.

**Consequences.** The Vercel config is reviewable in-repo; the preview deploy
is the validation gate for the tracing configuration (smoke `GET /api/chain`
and the corpus routes).

### ADR-006 — Expert API keys for CLI attestation posts

**Context.** The local CLI must link an on-chain attestation to the persisted
sealed case. The wallet that signs on-chain (seed-derived, dev machine) and
the browser wallet are typically different key sets — matching their
addresses would break the legitimate flow.

**Decision.** First expert login issues a long-lived API key, shown once,
hashed at rest (`experts.api_key_hash`). The CLI sends it with
`POST /api/attestations`; the server resolves the sealed bundle by
`bundleHash` and additionally verifies ownership: the bundle's
`expert_address` must equal the expert record the key belongs to. Key
compromise → rotate by re-issue; the key never authorizes anything beyond
attestation posts for the owner's own bundles.

**Rejected.**
- *Address-matching CLI wallet ↔ browser wallet:* different key sets by
  design; would refuse legitimate flows.
- *Unauthenticated posts with chain-side verification only:* a valid tx from
  anywhere could be linked to someone else's bundle in the display layer.

**Consequences.** One more secret in the expert's environment
(`VELO_API_KEY`); ownership checks are server-side and testable; the trust
model stays honest — the linkage is authenticated, and the on-chain facts are
separately chain-verified (ADR-003).

## Español

### ADR-001 — Vercel + Neon, sin proving hosteado

**Contexto.** El MVP necesita el frontend alcanzable por cualquiera (J1),
casos sellados persistidos y consultables (J2) y el estado de atestación
on-chain visible (J4). El camino de *escritura* de atestaciones necesita un
proof server, estado privado en LevelDB, un keystore cifrado local y una pila
de dependencias que solo corre en Bun — nada de eso puede ni debería correr
en infraestructura serverless compartida (ver ADR-003).

**Decisión.** Hostear el frontend Next.js en **Vercel**; persistir los casos
sellados y el registro de roles de peritos en **Neon** (Postgres serverless)
vía Drizzle. Sin backend de proving hosteado.

**Rechazado.**
- *Solo Vercel (sin BD):* el MVP requiere casos sellados persistidos y
  consultables — el estado en memoria o solo-en-la-respuesta no sobrevive
  entre invocaciones.
- *Backend full-cloud (GCP/AWS/Azure):* el único motivo genuino para
  infraestructura propia es el proving ZK server-side, y eso pertenece a la
  máquina del perito según el modelo de amenazas.
- *Backend de proving hosteado:* pone claves de firma y estado privado en
  infraestructura compartida — contradice la historia de seguridad que el
  producto existe para hacer realidad.

**Consecuencias.** El filesystem serverless y los timeouts de Vercel limitan
lo que puede correr ahí (lecturas, sellado, verificación — todo cómputo
puro); toda capacidad de escritura on-chain queda en tooling local. Un
Postgres administrado que operar; las connection strings se vuelven los
primeros secretos reales del repositorio.

### ADR-002 — Corpus servido estáticamente en el build

**Contexto.** El corpus (14 casos, 6 peritos) se lee de la raíz del repo en
cada request vía `resolve(process.cwd(), "..")` — un layout que no existe en
el runtime serverless de Vercel, donde solo están los archivos trazados y
`process.cwd()` no es el repo.

**Decisión.** Hacer estáticas las rutas de API del corpus:
`export const dynamic = "force-static"` en `/api/cases` y `/api/peritos`;
`generateStaticParams` enumerando el corpus en `/api/cases/[id]`. Next.js las
evalúa durante `next build`, cuando el layout del repo existe; el JSON se
sirve desde el CDN.

**Rechazado.**
- *Fs en runtime vía `outputFileTracingIncludes` + `VELO_REPO_ROOT`:*
  funciona, pero acopla el comportamiento runtime a paths internos de Vercel
  — frágil ante cambios de la plataforma.
- *Copia del corpus dentro de `frontend/` en el build:* una segunda copia de
  los mismos datos es exactamente el riesgo de deriva que documentó el red
  team F5.

**Consecuencias.** Cambiar el corpus requiere un redeploy — aceptable: el
corpus es data commiteada, así que en la práctica ya era así. El desarrollo
local sigue leyendo la raíz del repo directamente (sin cambios).

### ADR-003 — Atestación local, lecturas web

**Contexto.** Llamar al circuito `attest` del contrato requiere witnesses,
una wallet con fondos y el proof server local; la pila cliente guarda estado
privado en LevelDB y claves en un store cifrado local. Esto no puede correr
en Vercel — y según la tesis de VELO no debería: las claves y la evidencia
pertenecen a la máquina del perito.

**Decisión.** Las escrituras quedan locales: `deploy/attest-case.ts`
(existente, probado en `preview`) produce las atestaciones; el CLI publica el
registro (`{bundleHash, txHash, commitment}`) en la API web (ADR-006). La app
web solo lee: estado de cadena vía el existente `readOnChainLedger()` /
`GET /api/chain` (los bindings del contrato están commiteados, así que corre
en Vercel), casos sellados vía la base de datos. Esto extiende la separación
lectura/escritura ya documentada en [`CHAIN.md`](./CHAIN.md).

**Modelo de confianza del panel de verificación — dos clases, etiquetadas por
separado en la UI:**
- **chain-verified** — el commitment está presente en el mapa `caseVerdicts`
  on-chain con el veredicto declarado. Legible vía `GET /api/chain` en
  cualquier lugar donde corran los bindings commiteados, incluido Vercel.
- **expert-reported** — el valor del commitment en sí, provisto por el perito
  al publicar el registro. El salt es privado (por caso, en el estado privado
  del perito), así que el commitment no puede recomputarse solo con el
  bundle; el vínculo se ancla en la autenticación por API key más la
  verificación de pertenencia (ADR-006), y en la verificación on-chain de
  membresía.

**Rechazado / diferido.** Atestación desde el navegador. La API v4 del
connector expone proving delegado a la wallet (`getProvingProvider` +
`balanceUnsealedTransaction` + `submitTransaction`; 1AM patrocina proving y
dust), así que es un camino post-MVP real — condicionado a servir los
assets ZK y la configuración WASM/webpack desde el frontend, la parte
sabidamente dolorosa del trabajo frontend en Midnight (`CHAIN.md`, "What is
not built").

**Consecuencias.** La app web nunca toca claves de firma ni generación de
pruebas; un perito sin tooling local puede sellar y consultar pero no atestar
— se dice en la UI, no se esconde.

### ADR-004 — Identidad por wallet, lecturas públicas, sin contraseñas

**Contexto.** Los peritos necesitan una identidad asociada a sus sellos
persistidos (J2). La API v4 del connector de Midnight (`ConnectedAPI`) expone
direcciones, balances y configuración — pero **ninguna primitiva de firma de
mensajes**, así que la prueba criptográfica de posesión no está disponible en
la superficie oficial de la API.

**Decisión.** Roles: anónimo (navegar/demo, nada persiste), perito (wallet
conectada + presente en el registro de roles → persiste y atesta),
revisor/juez (sin cuenta — lecturas públicas y el panel `/verify`).
Autenticación = conexión de wallet; el cliente presenta la dirección de la
wallet conectada, el servidor emite una cookie JWT httpOnly firmada
(`AUTH_SECRET`). Sin contraseñas, sin email, sin OAuth.

**Limitación conocida (aceptada).** La dirección es atestada por la UI: el
servidor confía en lo que reporta el cliente conectado. Es suficiente para el
gating de roles del MVP (asociar identidad a acciones, no proteger secretos);
no sería suficiente para nada financiero. El endurecimiento con prueba de
posesión es post-MVP y necesitaría una superficie de firma que el connector
oficial hoy no provee.

**Consecuencias.** Cero gestión de credenciales para los usuarios; el registro
de roles (tabla `experts`, sembrada con los peritos sintéticos) es la única
fuente de verdad de roles; wallets desconocidas pueden conectarse pero no
persistir (AC-J2.6).

### ADR-005 — Configuración de despliegue del monorepo

**Contexto.** Monorepo con npm workspaces: el frontend depende del paquete
raíz `velo` (`file:..`, resuelto a `./dist/src/*`), así que el paquete raíz
debe compilarse antes de `next build`. Vercel necesita instrucciones de
instalación/build sin ambigüedad, y el `frontend/package-lock.json` anidado
(que se deja en su lugar — la limpieza del repo está fuera de alcance) podría
confundir la resolución del lockfile.

**Decisión.** Proyecto Vercel: Root Directory `frontend`, framework Next.js,
Node 20+. `frontend/vercel.json` fija un `installCommand` explícito (`cd ..
&& npm ci` — resolver siempre desde el lockfile de la raíz del workspace) y
`buildCommand` (`npm run build:deploy` = `tsc` de la raíz y después `next
build`). `next.config.mjs` fija `outputFileTracingRoot` en la raíz del repo y
`outputFileTracingIncludes` para todo lo que se carga por paths calculados en
runtime: `contracts/velo.compact` (el marcador de raíz),
`contracts/managed/**` (bindings commiteados), `deploy/managed-shim/*.json`
(artefacto de dirección del contrato), `cases/*.json`,
`peritos-syntetic/*.json`.

**Rechazado.** Reestructurar el monorepo para simplificar el deploy — el
layout de workspaces es estructural para el desarrollo local y para los
imports directos del motor desde el frontend.

**Consecuencias.** La configuración de Vercel es revisable en el repo; el
preview deploy es la compuerta de validación de la configuración de tracing
(smoke de `GET /api/chain` y de las rutas del corpus).

### ADR-006 — API keys de perito para publicar atestaciones desde el CLI

**Contexto.** El CLI local debe vincular una atestación on-chain con el caso
sellado persistido. La wallet que firma on-chain (derivada de seed, máquina
de desarrollo) y la wallet del navegador suelen ser pares de claves distintos
— comparar sus direcciones rompería el flujo legítimo.

**Decisión.** El primer login del perito emite una API key de larga duración,
mostrada una sola vez, hasheada en reposo (`experts.api_key_hash`). El CLI la
envía con `POST /api/attestations`; el servidor resuelve el bundle por
`bundleHash` y además verifica pertenencia: el `expert_address` del bundle
debe coincidir con el registro de perito al que pertenece la key. Key
comprometida → se rota re-emitiendo; la key nunca autoriza nada más que
publicar atestaciones de los bundles de su dueño.

**Rechazado.**
- *Comparar direcciones wallet CLI ↔ navegador:* pares de claves distintos
  por diseño; rechazaría flujos legítimos.
- *Publicaciones sin autenticación con verificación solo on-chain:* una tx
  válida de cualquier origen podría vincularse al bundle de otro en la capa
  de visualización.

**Consecuencias.** Un secreto más en el entorno del perito (`VELO_API_KEY`);
los chequeos de pertenencia son server-side y testeables; el modelo de
confianza se mantiene honesto — el vínculo está autenticado, y los hechos
on-chain se verifican por separado (ADR-003).
